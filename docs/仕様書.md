# 飲み会管理 Discord Bot 仕様書

本ドキュメントは [要件定義.md](要件定義.md) を元に作成した実装仕様書である。

---

## 1. 概要

サーバー(ギルド)内の飲み会(オフ会)を管理する Discord Bot。
イベントごとに専用チャンネル・ロールを自動生成し、出欠・飲み会(お店)・支払受領記録を一元管理する。
複数サーバーへの導入を前提としたマルチテナント設計とする。

## 3. システム構成

Bot(JDA)と Web コンソール(Ktor)は**同一プロセス(単一 JVM)**で動作し、Service 層を共有する。
これにより Web からの操作も Discord へ即時反映される(詳細は [Web仕様書.md](Web仕様書.md))。

```
┌───────────────────────┐      ┌───────────────────────────┐
│ Discord (JDA Gateway) │      │ ブラウザ (Web コンソール) │
└──────────┬────────────┘      └──────────┬────────────────┘
           │ interaction                  │ HTTP(S)
┌──────────▼──────────────────────────────▼────────────────┐
│  app コンテナ(単一 JVM)                                 │
│  ┌──────────────────┐        ┌──────────────────┐        │
│  │ bot モジュール   │        │ web モジュール   │        │
│  │ Listener →       │        │ Ktor Route       │        │
│  │ Command/Button   │        │ (Session/認可)   │        │
│  │ Handler          │        │                  │        │
│  └────────┬─────────┘        └────────┬─────────┘        │
│           └───────────┬───────────────┘                  │
│                ┌──────▼──────┐                           │
│                │   Service   │  core モジュール          │
│                └──┬───────┬──┘                           │
│      ┌────────────▼──┐  ┌─▼───────────┐                  │
│      │ DiscordGateway│  │ Repository  │                  │
│      │ (JDA 実装)    │  │ (Exposed)   │                  │
│      └───────────────┘  └──────┬──────┘                  │
└────────────────────────────────┼─────────────────────────┘
                                 │ JDBC
                      ┌──────────▼──────────┐
                      │ PostgreSQL コンテナ │
                      └─────────────────────┘
```

### レイヤ責務

| レイヤ | 責務 |
| --- | --- |
| Listener | JDA イベントの受信とルーティング(`onSlashCommandInteraction` / `onButtonInteraction` / `onModalInteraction`) |
| Command / Interaction Handler | 入力バリデーション、権限チェック、応答生成。トランザクション境界の起点 |
| Service | 業務ロジック(採番・状態遷移・上限チェック等)。DB 操作と Discord 操作の整合を担保 |
| Repository | Exposed によるテーブル CRUD |
| DiscordGateway | チャンネル / ロール / 権限の生成・変更・削除の抽象化(インターフェースは core、JDA 実装は bot モジュール) |
| Web Route (Ktor) | HTTP ルーティング、セッション・認可チェック、テンプレート描画。Handler 層と同格で Service を呼ぶ |

## 4. マルチテナント設計方針

- すべての永続データは `guild_id` を保持し、ギルド単位で完全に分離する。
- 全クエリは `guild_id` を条件に含める(他ギルドのデータへアクセスさせない)。
- スラッシュコマンドは **ギルドコマンド**として各ギルドに登録する(グローバルコマンドは使用しない、もしくは反映遅延を許容してグローバル登録し `guild_id` で分離)。本仕様では **グローバル登録 + guild_id 分離**を採用し、実行時に `event.guild` からギルドを解決する。
- Bot 導入直後は設定が空のため、`/settings` による初期設定完了までイベント作成系コマンドは拒否する。

## 5. 設定項目

| 設定キー | 内容 | 必須 |
| --- | --- | --- |
| `event-category` | イベントチャンネルを作成するカテゴリ | ○ |
| `archive-category` | アーカイブ先カテゴリ | ○ |
| `admin-role` | 運営ロール | ○ |
| `log-channel` | 操作ログ(監査ログ)出力チャンネル | ○ |
| `recruit-channel` | 募集メッセージ(参加ボタン)を投稿する公開チャンネル | ○ |

> **設計判断:** 参加前ユーザーはイベントチャンネルを閲覧できない(ロール付与で初めて閲覧可能)。
> そのため参加ボタンは公開の `recruit-channel` に投稿された募集メッセージ上に表示する。
> イベントチャンネル自体は非公開のまま維持する。

設定は `/settings set` で運営ロール保持者のみ変更可能。`/settings show` で現在値を表示する。

## 6. データモデル

Discord のスノーフレーク ID(guild/channel/role/user)はすべて `BIGINT` として保持する。

### 6.1 ER 概要

```
guild_settings (1) ─┐
                    │
event_counters (1)  │  ギルドごとの採番カウンタ
                    │
events (N) ─────────┤ guild_id
   │                │
   ├─ event_participants (N)
   └─ parties (N)
         └─ payments (N)
```

### 6.2 テーブル定義 (DDL)

```sql
-- ギルド設定
CREATE TABLE guild_settings (
    guild_id            BIGINT PRIMARY KEY,
    event_category_id   BIGINT,
    archive_category_id BIGINT,
    admin_role_id       BIGINT,
    log_channel_id      BIGINT,
    recruit_channel_id  BIGINT,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ギルドごとの通し番号カウンタ(欠番を許容するため events とは独立)
CREATE TABLE event_counters (
    guild_id     BIGINT PRIMARY KEY,
    next_number  INTEGER NOT NULL DEFAULT 1
);

-- イベント本体
CREATE TABLE events (
    id                BIGSERIAL PRIMARY KEY,
    guild_id          BIGINT NOT NULL,
    number            INTEGER NOT NULL,          -- 第n回 の n
    name              VARCHAR(80) NOT NULL,
    area              VARCHAR(80) NOT NULL,
    event_date        DATE,                      -- オプション
    status            VARCHAR(16) NOT NULL DEFAULT 'RECRUITING', -- RECRUITING / ARCHIVED
    channel_id        BIGINT NOT NULL,
    role_id           BIGINT NOT NULL,
    recruit_message_id BIGINT,                   -- 募集メッセージ(参加ボタン)の ID
    organizer_user_id BIGINT NOT NULL,           -- 幹事(作成者)
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    archived_at       TIMESTAMPTZ,
    CONSTRAINT uq_events_guild_number UNIQUE (guild_id, number)
);
CREATE INDEX idx_events_guild_status ON events (guild_id, status);

-- 出欠(イベント単位)
CREATE TABLE event_participants (
    id         BIGSERIAL PRIMARY KEY,
    event_id   BIGINT NOT NULL REFERENCES events(id) ON DELETE CASCADE,
    user_id    BIGINT NOT NULL,
    joined_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_participant UNIQUE (event_id, user_id)
);

-- 飲み会(お店単位)
CREATE TABLE parties (
    id            BIGSERIAL PRIMARY KEY,
    event_id      BIGINT NOT NULL REFERENCES events(id) ON DELETE CASCADE,
    order_no      INTEGER NOT NULL,              -- 1軒目=1, 2軒目=2 ...
    shop_name     VARCHAR(120) NOT NULL,
    total_amount  BIGINT,                        -- 会計金額(円)。未確定時 NULL
    note          VARCHAR(255),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_party_order UNIQUE (event_id, order_no)
);

-- 支払受領記録(誰からいくら受け取ったか)
CREATE TABLE payments (
    id           BIGSERIAL PRIMARY KEY,
    party_id     BIGINT NOT NULL REFERENCES parties(id) ON DELETE CASCADE,
    payer_user_id BIGINT NOT NULL,               -- 支払った参加者
    amount       BIGINT NOT NULL,                -- 受領金額(円)
    recorded_by  BIGINT NOT NULL,                -- 記録した幹事/運営
    received_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_payments_party ON payments (party_id);
```

> **割り勘計算は Bot では行わない。** `payments` は受領実績のみを保持する(要件 line 76)。

## 7. 採番(第n回)仕様

- ギルド全体の通し番号。イベント削除後も既存番号は変更せず、**欠番を許容**する。
- 採番は `event_counters` を用いてアトミックに行う:

```sql
INSERT INTO event_counters (guild_id, next_number) VALUES (:guildId, 2)
ON CONFLICT (guild_id) DO UPDATE SET next_number = event_counters.next_number + 1
RETURNING event_counters.next_number - 1 AS assigned_number;
```

- 同時作成による整合性崩れ(先行作成イベントが削除され番号が飛ぶ等)は、運営が `/event renumber` で手動修正できる。
  - `uq_events_guild_number` 制約により、既存番号との重複は登録時に拒否される。
- 既存サーバーへの導入時など、`event_counters.next_number` の初期値を運営が `/settings next-number` で手動設定できる。
  - 記録済みイベントの最大番号以下は指定不可(整合性維持のため)。

## 8. 権限モデル

| 操作 | サーバー参加者 | 幹事(作成者) | 運営(admin-role) |
| --- | :---: | :---: | :---: |
| イベント作成 | ○ | ○ | ○ |
| イベント編集 | × | ○(自分のイベント) | ○ |
| アーカイブ化 | × | ○(自分のイベント) | ○ |
| 飲み会登録 | × | ○(自分のイベント) | ○ |
| 支払管理 | × | ○(自分のイベント) | ○ |
| イベント削除 | × | × | ○ |
| 手動採番修正 | × | × | ○ |
| 設定変更 | × | × | ○ |
| 参加 | ○ | ○ | ○ |
| 参加キャンセル | ○ | ×(幹事は不可) | ○(自身が参加者の場合のみ) |
| 全イベントチャンネル閲覧 | × | × | ○ |

- 幹事はイベント作成者 1 人のみ。複数化・権限引き継ぎは実装しない(要件 line 70)。
- 幹事不在時は運営が削除して作り直す(要件 line 71)。
- 権限チェックは Handler 層で実施。`admin-role` 保持者は常に幹事権限を包含する。
- 幹事は自身のイベントの参加をキャンセルできない(進行管理者としてイベントに留まり続ける必要があるため)。キャンセルしたい場合は `/event delete` で運営に削除を依頼する。

## 9. Discord インタラクション設計

### 9.1 スラッシュコマンド

| コマンド | オプション | 実行者 | 概要 |
| --- | --- | --- | --- |
| `/settings set` | `key`, `value(チャンネル/ロール)` | 運営 | 設定項目の登録・変更 |
| `/settings show` | — | 運営 | 現在の設定を表示 |
| `/settings next-number` | `number`(次の番号) | 運営 | 次回イベントの「第n回」採番を手動設定 |
| `/event create` | `name`(必須), `area`(必須), `date`(任意) | 全員 | イベント作成 |
| `/event edit` | `name`, `area`, `date`(いずれも任意) | 幹事/運営 | イベント情報編集(実行はイベントチャンネル内) |
| `/event archive` | — | 幹事/運営 | アーカイブ化(イベントチャンネル内で実行) |
| `/event delete` | — | 運営 | 削除(確認ダイアログあり) |
| `/event renumber` | `number`(新番号) | 運営 | 第n回の手動修正 |
| `/party add` | `shop`(必須), `order`(任意), `amount`(任意) | 幹事/運営 | 飲み会(お店)登録 |
| `/party list` | — | 幹事/運営/参加者 | 飲み会一覧 |
| `/payment add` | `party`(お店選択), `payer`(ユーザー), `amount` | 幹事/運営 | 受領記録の登録 |
| `/payment list` | `party`(任意) | 幹事/運営 | 受領記録一覧・合計 |

- チャンネル内で実行するコマンド(`edit`/`archive`/`delete`/`party`/`payment`)は、実行チャンネルの `channel_id` からイベントを解決する。イベントチャンネル外での実行はエラー応答。
- 応答は原則 **ephemeral**(実行者のみ表示)。募集メッセージ等の公開通知のみ通常メッセージ。

### 9.2 ボタン

| customId | 表示場所 | 動作 |
| --- | --- | --- |
| `event:join:{eventId}` | 募集チャンネルの募集メッセージ | 参加(ロール付与) |
| `event:leave:{eventId}` | イベントチャンネル | 参加キャンセル(ロール剥奪) |
| `event:delete:confirm:{eventId}` | 削除確認ダイアログ | 削除実行 |
| `event:delete:cancel:{eventId}` | 削除確認ダイアログ | 削除中止 |

### 9.3 モーダル(任意)

- 支払登録・編集など複数項目入力はモーダルで受け付けてもよい(実装選択)。

## 10. 機能仕様(詳細)

### 10.1 初期設定

1. Bot をギルドに招待。
2. 運営が `/settings set` で `event-category` / `archive-category` / `admin-role` / `log-channel` / `recruit-channel` を登録。
3. 未設定項目がある間、`/event create` 等は「初期設定が未完了です」として拒否。

### 10.2 イベント作成 `/event create`

**入力:** イベント名、開催エリア、日付(オプション)

**処理フロー:**
1. 初期設定完了チェック。
2. カテゴリ内チャンネル数チェック(§10.8)。上限時は作成拒否。
3. `event_counters` で番号 `n` を採番(§7)。
4. Discord 上に以下を生成(DiscordGateway):
   - ロール `第{n}回参加者`
   - チャンネル `第{n}回-{イベント名}` を `event-category` 配下に作成
     - 権限: `@everyone` 閲覧不可 / 該当ロール 閲覧・送信可 / `admin-role` 閲覧・送信可
5. `recruit-channel` に募集メッセージ(Embed: イベント名/エリア/日付/幹事)+ `参加` ボタンを投稿し、`recruit_message_id` を保存。
6. `events` に登録(status=RECRUITING、organizer=実行者)。
7. 幹事は参加必須のため、`event_participants` に幹事自身を自動登録し、該当ロールを幹事に付与する。

**整合性:** Discord 生成と DB 登録は、いずれか失敗時に生成済みリソース(ロール/チャンネル/参加登録)をロールバック削除する(補償処理)。

- チャンネル名は Discord の命名規則(小文字化・スペース→ハイフン等)に自動変換される点を許容。表示名は Embed で担保。

### 10.3 イベント参加 `event:join`

1. 対象イベントが `RECRUITING` であることを確認(ARCHIVED/削除済みは不可、要件 line 48)。
2. `event_participants` に UPSERT(既参加なら「参加済み」応答)。幹事はイベント作成時点で自動登録済みのため、幹事自身が改めて参加ボタンを押すと「既に参加しています」となる。
3. 該当ロールを実行ユーザーに付与 → チャンネル閲覧可能に。
4. 受付締切の概念なし。アーカイブ前は常に参加可能(要件 line 49)。

### 10.4 参加キャンセル `event:leave`

1. 実行者が幹事(`organizer_user_id`)でないことを確認。幹事本人による参加キャンセルは拒否する。
2. `event_participants` から削除。
3. ロールを剥奪 → チャンネル閲覧不可に。
4. アーカイブ済みイベントではキャンセル不可。

### 10.5 アーカイブ化 `/event archive`

1. 実行者が幹事または運営か確認。
2. チャンネルを `archive-category` へ移動(上限チェックあり、§10.8)。
3. 権限変更: **全ロールの送信権限を剥奪**(閲覧のみ)。アーカイブ前に参加していた(ロール付与済み)ユーザーのみ履歴閲覧可(要件 line 57)。
   - ロールは削除せず維持(閲覧権限の担保のため)。
4. 募集メッセージの参加ボタンを無効化(disabled)。
5. `events.status = ARCHIVED`、`archived_at` を記録。

### 10.6 イベント削除 `/event delete`

1. 実行者が運営か確認(幹事は不可)。
2. **確認ダイアログ**(ボタン `削除する` / `キャンセル`)を ephemeral 表示(要件 line 61)。
3. `削除する` 押下時:
   - Discord のチャンネル・ロールを削除。
   - 募集メッセージを削除(または無効化)。
   - `events`(および CASCADE で participants/parties/payments)を削除。
   - **監査ログ**を `log-channel` に出力(§11)。
4. 採番カウンタは戻さない(欠番許容)。

### 10.7 飲み会(お店)と支払管理

**飲み会登録 `/party add`(要件 line 64-67):**
- 幹事が店情報を登録すると飲み会が発生。1イベントに複数(1軒目/2軒目…)可。
- `order_no` 未指定時は既存最大 +1 を自動採番。
- 出欠はイベント単位でのみ管理し、飲み会単位の個別出欠は管理しない。

**支払管理 `/payment add`(要件 line 73-76):**
- 会計発生時、飲み会(お店)ごとに会計金額 `total_amount` を登録可能。
- 参加者から受け取った金額を `payments` に記録(payer_user_id, amount)。
- 割り勘計算は行わない。受領記録のみ管理。
- `/payment list` で店ごとの受領一覧と合計を表示。

### 10.8 カテゴリ内チャンネル上限対応(要件 line 41-43)

- Discord 仕様: 1 カテゴリ最大 50 チャンネル。
- イベント作成 / アーカイブ移動の前にカテゴリ内チャンネル数を確認:
  - **警告閾値**(既定 45 チャンネル)到達時: 処理は継続するが `log-channel` にアラート出力。
  - **上限**(50)到達時: 新規作成 / アーカイブ移動を**拒否**しエラー応答。

## 11. ログ / 監査

`log-channel` に以下を Embed で出力する。閲覧権限は運営が手動設定(要件 line 16)。

| イベント | 出力内容 |
| --- | --- |
| イベント削除 | 実行者、イベント名(第n回)、実行日時(要件 line 62) |
| カテゴリ上限警告 | 対象カテゴリ、現在チャンネル数 |
| 手動採番修正 | 実行者、旧番号→新番号 |

アプリケーションログ(SLF4J/Logback)は標準出力に出し、Docker のログドライバで収集する。

## 12. エラーハンドリング / 制約

- Discord API のレートリミットは JDA のキューイングに委譲。大量操作(削除時のメッセージ等)は考慮不要(チャンネルごと削除)。
- Discord 操作と DB 更新の不整合は補償処理でロールバック(§10.2)。整合が取れない場合は `log-channel` に警告。
- 文字数上限: イベント名 80、エリア 80、店名 120(DB 定義に準拠)。
- 金額は円単位の整数(`BIGINT`)。負数は拒否。

## 13. WEB コンソール

Bot と**同一プロセス(単一 JVM)**で Ktor HTTP サーバーを起動し、Service 層を共有する構成とする。
Web からの操作も Bot と同じコードパス(Service → DiscordGateway)を通るため、イベント編集・参加などの結果は Discord 側(チャンネル / ロール / 募集メッセージ)へ即時反映される。

- 認証: Discord OAuth2(`identify` スコープ)+ 暗号化 Cookie セッション。
- フロントエンド: SSR(Ktor + FreeMarker)。JS は最小限。
- 権限: §8 と同一の権限モデルを適用。ロール判定は毎リクエスト JDA(DiscordGateway)から解決するため、Discord 側のロール変更が即座に Web にも反映される。
- 閲覧範囲(要件 line 82-85): 一般参加者は自分の参加履歴・支払のみ / 幹事は自イベントの管理 / 運営は全件。

画面一覧・ルーティング・OAuth2 フロー・セッション管理・セキュリティの詳細は [Web仕様書.md](Web仕様書.md) を参照。

## 14. Docker / デプロイ構成

### 14.1 コンテナ構成

- `bot`: Kotlin アプリ(JDA + Ktor)。Web コンソールをポート 8080 で公開。
- `db`: PostgreSQL 16。

### 14.2 環境変数

| 変数 | 内容 |
| --- | --- |
| `DISCORD_TOKEN` | Bot トークン(シークレット) |
| `DB_URL` | `jdbc:postgresql://db:5432/nomibot` |
| `DB_USER` / `DB_PASSWORD` | DB 認証情報 |
| `LOG_LEVEL` | ログレベル(既定 INFO) |
| `CHANNEL_WARN_THRESHOLD` | カテゴリ警告閾値(既定 45) |
| `DISCORD_CLIENT_ID` / `DISCORD_CLIENT_SECRET` | OAuth2 クライアント認証情報(Web コンソール) |
| `PUBLIC_BASE_URL` | Web コンソールの公開 URL(OAuth2 redirect_uri の組み立てに使用) |
| `SESSION_ENCRYPT_KEY` / `SESSION_SIGN_KEY` | セッション Cookie の暗号化・署名キー |
| `WEB_PORT` | Web コンソールのポート(既定 8080) |

### 14.3 docker-compose.yml(例)

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: nomibot
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER}"]
      interval: 5s
      timeout: 5s
      retries: 5

  bot:
    build: .
    depends_on:
      db:
        condition: service_healthy
    ports:
      - "8080:8080"
    environment:
      DISCORD_TOKEN: ${DISCORD_TOKEN}
      DISCORD_CLIENT_ID: ${DISCORD_CLIENT_ID}
      DISCORD_CLIENT_SECRET: ${DISCORD_CLIENT_SECRET}
      PUBLIC_BASE_URL: ${PUBLIC_BASE_URL}
      SESSION_ENCRYPT_KEY: ${SESSION_ENCRYPT_KEY}
      SESSION_SIGN_KEY: ${SESSION_SIGN_KEY}
      DB_URL: jdbc:postgresql://db:5432/nomibot
      DB_USER: ${DB_USER}
      DB_PASSWORD: ${DB_PASSWORD}
    restart: unless-stopped

volumes:
  db-data:
```

- 起動時に Flyway でマイグレーションを適用してから JDA を接続し、JDA の ready 後に Ktor(Web コンソール)を起動する。
- 本番公開時は Web コンソールの前段にリバースプロキシを置き TLS 終端する(Web仕様書.md §8)。
